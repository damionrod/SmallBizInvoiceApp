# V61.69F — Payroll Browser Runtime Fix

## Scope
Correct only the observed Payroll browser runtime crash from V61.69E. No RLS, database, payroll records, calculations, tax rules, tenant filters, or unrelated modules changed.

## Observed browser root cause
DIAG1 proved the browser loaded the diagnostic build and resolved Care correctly, then threw:
`TypeError: Cannot read properties of null (reading 'country_code')` at Payroll `renderSettings()`.

The exact null object was `state.settings`. The failing expression was `state.settings.country_code`.

### Why it was null
V61.69D/E deliberately changed Payroll to clear operational state before loading the newly authorised tenant. During `load()`, after `current_business_id()` matched the SAAS business, the code assigned `state.businessId`, cleared operational arrays, and immediately called `renderAll()` **before** `payroll_settings` had been fetched and assigned to `state.settings`.

`renderAll()` includes `renderSettings()`. On a fresh page/module runtime `state.settings` is initially `null`, so `renderSettings()` dereferenced `state.settings.country_code` and the async `load()` promise aborted before `ensureDefaults`, the settings query, and all 12 operational queries could complete. This is why the database/RLS simulations worked while the real browser showed zero employees.

DIAG1 also showed `state.businessId: null` at `load:start`. That is expected for a newly initialised Payroll module; the bug was that rendering business/country-dependent Settings was allowed before the authorised Payroll tenant/settings context had finished initialising.

## Correction
1. Added `clearTenantRuntimeState()` to clear operational arrays **and tenant-dependent Payroll configuration state** (`settings`, country rules/countries, pay items, leave types, document types) before a new tenant load.
2. Added `renderOperationalState()` for the safe loading/error phase. It renders empty operational UI only and deliberately does not call `renderSettings()`.
3. Loading/error branches now use `renderOperationalState()` until Payroll settings exist.
4. `renderSettings()` explicitly returns while `state.settings` is not initialised. This is a lifecycle precondition, not a fallback country value and not optional chaining around a required object.
5. The successful path is unchanged in principle: authorised business -> seed/check defaults -> fetch that business's payroll_settings -> resolve country/rules -> fetch all explicitly business-scoped operational tables -> reject late response if business changed -> assign state -> `renderAll()`.
6. Existing V61.69D/E business-id predicates and late-business-response guard remain intact.

## Tenant isolation
No tenant filter was removed or weakened. `current_business_id()` must still equal the SAAS active business. Every V61.69E Payroll operational query remains explicitly filtered by `requestBid`. Query errors still fail closed and do not display previous-tenant records.

## GoTrueClient warning investigation
Two Supabase browser clients are instantiated:
- `saas.js` creates the primary authenticated client stored in `state.client`.
- `app.js` independently calls `window.supabase.createClient(...)` in `initSupabase()` for legacy/core invoice/customer operations.

That explains the browser warning about multiple GoTrueClient instances. Payroll itself uses `window.SAAS.client()` only, so the second `app.js` client is not the cause of the observed line-511 crash. It is left unchanged in V61.69F to avoid an unrelated authentication/client refactor. It should be handled as a separate cleanup item after this release blocker is closed.
