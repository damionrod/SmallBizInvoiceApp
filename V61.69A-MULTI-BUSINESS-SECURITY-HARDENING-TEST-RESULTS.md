# V61.69A Multi-Business Security Hardening — Test Results

Date: 2026-09-15  
Scope: Gate A + Gate B security hardening only. **STOP after Gate B.** No Add Another Business/provisioning/switcher UX was added.

## Executive result

**Gate A: PASS for the scoped hardening.** The active-business resolver no longer trusts legacy `profiles.business_id` without active membership; Accountant Centre tenant policies are active-business constrained; the two mutable search-path warnings are removed; direct anonymous execution of SECURITY DEFINER functions fell from 48 advisor findings to **1 intentional pre-login RPC** (`v35_checkout_available`). The four RLS/no-policy tables remain intentionally direct-client-denied and RPC/service-only.

**Gate B: PASS for database/RLS simulation; authenticated browser E2E remains required.** Transactional multi-business simulations proved Business B is invisible while Business A is active, becomes available after switching to B, and Business A becomes unavailable through active-tenant Accountant Centre access. Suspended membership falls back to the still-authorised legacy/home business. No temporary fixture persisted.

## Original vulnerabilities

1. `current_business_id()` validated `active_business_id`, but its fallback returned `profiles.business_id` without validating active membership. A manipulated/stale legacy field could therefore become an authority source.
2. `accounting_export_mappings`, `tax_export_mappings`, `accounting_destination_accounts`, and `accounting_exports` used membership-only RLS. A user who belonged to B could address B while A was selected.
3. PostgreSQL default `PUBLIC EXECUTE` left many SECURITY DEFINER helpers directly callable. Supabase advisor reported 48 anonymous and 80 authenticated-callable SECURITY DEFINER functions before hardening.
4. `v6148_role_default_read` and `v6148_role_default_write` had mutable `search_path` advisor warnings.
5. Invoice → customer locality was not protected by a tenant-local relationship guard. Invoice → job already had an existing guard; V61.69A adds a combined defensive guard without removing the existing one.

## Exact fixes

- Replaced only `current_business_id()` with membership-validated active + legacy fallback logic. Super Admin retains intentional selected/home context.
- Added `v6169a_accountant_centre_access(business_id, write)` and replaced the four Accountant Centre membership-only policy sets with selected-active-business policies.
- Preserved Accountant/Bookkeeper mapping/destination write access after switching to their authorised business; report-read permission remains the read boundary.
- Added `v6169a_validate_invoice_business_refs()` trigger for invoice → customer and invoice → job same-business enforcement.
- Set explicit `search_path=public` on the two reported role-default functions.
- Removed default PUBLIC EXECUTE from SECURITY DEFINER functions while preserving explicit authenticated/service-role grants. Trigger-only helpers no longer need direct anon/auth API execution. `v35_checkout_available()` intentionally remains anonymous for pre-login signup/payment UX.
- No historical migration was rewritten. No frontend, Edge Function, Netlify Function, Stripe, subscription, module, or customer-facing workflow was changed.

## Same-pattern audit across database/codebase

The database policy search found exactly the four known Accountant Centre areas using membership-only tenant access without `current_business_id()`. They were fixed. Other membership-based operations were reviewed rather than blindly converted:

- `business_memberships` / business switching visibility — **intentional cross-business membership operation**; must be able to discover authorised businesses.
- business invitation acceptance/send/list — **business-switch/membership-management operation**; server Edge Function uses service role plus its own authenticated manager checks; no broad client table grant.
- Team/member management RPCs (`v6145_*`, `v6148_*`, `v6149_*`) — **membership-management operation**; role/owner/admin checks retained. These need authenticated E2E when the future switcher is introduced.
- Super Admin RPCs (`v33_*`, `v34_*`, `v36_*`, `v6151_admin_*`, V61.68 ruleset RPCs) — **intentional Super Admin cross-business operations**, each retaining Super Admin checks.
- Stripe/referral internal functions — **server/internal cross-business operation**, direct tenant execution remains unavailable where not explicitly granted.
- Normal module RLS (`invoices`, `customers`, expenses, bank, financials, payroll, jobs) — **active-business constrained** through `current_business_id()` and/or `v6147_can_*`.
- Frontend Accountant Centre direct queries all use `state.businessId`; database RLS now independently enforces that it equals the authorised selected business.
- No additional tenant table with the same membership-only RLS defect was found in the current public policy catalogue.
