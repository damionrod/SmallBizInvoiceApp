# V61.85 — Stripe Connect repeat-visit fix

## What caused the error

Creating a connected account and opening onboarding already used JSON. Looking
up that account on the next visit incorrectly sent the form-encoded Content-Type
used by Stripe API v1. Stripe API v2 rejects this header, including on GET requests.
The same lookup also used unindexed `include[]` parameters; v2 requires indexed
query parameters such as `include[0]`.

Reference: https://docs.stripe.com/api-v2-overview

## Scope

The only existing source file changed since the v61.84 package is
`supabase/functions/invoice-payments/index.ts`. Its account lookup now sends
`Content-Type: application/json` and indexed include parameters. It remains a GET
request, with no JSON request body. The existing account ID is reused.

The shared header helper, v1 invoice Checkout encoding, subscription billing,
frontend files, fee settings, database schema/policies, email logic, and webhook
settlement logic are unchanged. The v61.84 checkout-redirect fix is retained.
One regression test file and this release note are added.

## Deployment and verification

The corrected `invoice-payments` function was deployed to the connected Frindly
Supabase project (`oxsbzytwbphagcbilxud`) as version 3. Its deployed source was
read back and matched to the tested code. Custom authentication and payment-link
checks are unchanged; `verify_jwt` retains its existing `false` setting.

No database migration, Stripe account reset, or Netlify redeployment is needed
for this backend fix. Keep the updated source in GitHub so a later function
deployment does not restore the old lookup. This full ZIP includes the earlier
v61.84 frontend fixes, but v61.85 does not change frontend cache/version labels.

For a separate environment, deploy only this function after linking the intended
Supabase project:

```bash
supabase functions deploy invoice-payments --no-verify-jwt
```

## Tests

`tests/v6185-stripe-account-revisit.test.js` runs the real function source with
in-memory Stripe and Supabase substitutes, without real credentials or payments.
Tested with Node.js 24.19.0, using its built-in TypeScript stripping.

```bash
node --test tests/v6185-stripe-account-revisit.test.js
```

Five behavioral tests cover first setup followed by repeat visits, reuse of the
same account, fresh onboarding links, preservation of fee/partial-payment
settings, Stripe errors, partial invoice Checkout, and unchanged access checks.
The new tests reproduced the reported content-type error before the patch.
All 24 local test files passed after the patch. The separate authenticated
HTTP/database test was skipped because test credentials were not provided.
No real onboarding or payment was submitted during these tests.

## Signed-in check still required

1. Open https://frindly.co.nz/#settings/payments and sign in as the business owner.
   Use the hosted site, not a double-clicked `public/index.html` / `file://` copy.
   The local-file address was not the cause of the Stripe header error, but the
   hosted site gives onboarding a consistent HTTPS return address.
2. Refresh Payments. The existing Stripe setup should load without the JSON
   Content-Type error.
3. If setup is incomplete, continue the existing Stripe onboarding. Do not create
   another account or re-enter bank details merely to test this patch.
4. Return to Payments, navigate away, then open Payments a second time. Check that
   the existing account status loads again.

The account-specific, signed-in Stripe journey must still be confirmed by the
business owner; mocked tests and public endpoint checks do not replace it.
