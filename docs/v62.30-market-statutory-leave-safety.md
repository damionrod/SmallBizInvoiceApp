# v62.30 Market statutory leave save safety

This release hardens the existing exported `Payroll.recordStatutoryLeave` persistence path for NZ sick, bereavement and family-violence leave in days. It does not add a leave-processing screen, connect employee requests to payroll, recalculate historical records, alter statutory formulas or certify statutory compliance. Main/live is unchanged.

## Change

The old method performed working-day, leave-entry, calculation and entitlement writes in separate browser requests. A failed request could leave partial records, and `used_days` was calculated from cached browser state. The method also dereferenced a missing OWD result for an ineligible calculation.

One authenticated database command now validates and saves the complete supported bundle, audit and operation evidence in one transaction. It locks the employee, checks the loaded working-day/entitlement revisions, requires effective rule evidence, and increments days used from the stored period. Exact actor/input/request retries return the original saved result. Different input under the same request identifier is rejected. A second confirmed record for the same employee/date/code is refused; multiple partial-day entries on that date need a reviewed correction workflow rather than another insert.

Confirmed sick/family-violence entries require a reviewed, dated entitlement period. Existing grant/carry/period fields cannot be overwritten through a leave entry. New periods cannot overlap; dates must cover the entry, and the saved period cannot be overdrawn. These are persistence checks, not an independent statutory entitlement calculation. The existing client calculation engine, RDP/ADP selection and amounts remain unchanged. Rule snapshots must match the active NZ rows for the date; stale or unavailable rules fail closed. The command does not independently recompute the full statutory result from source payroll history.

Ineligible/non-required results can retain evidence without creating a leave entry or changing entitlement. Unconfirmed evidence is not promoted into paid leave. General notes and employer reason are omitted by the browser for family-violence leave; the transaction note and OWD reason are also suppressed server-side. Existing restricted calculation evidence is retained, not redacted or rewritten.

The browser retains the original request ID, figures and revisions for an uncertain retry within that page session. Definite database failures clear retry state. Duplicate clicks, a different pending input, changed business/account, reloaded Payroll state and malformed success responses cannot silently merge stale results. Closing the page loses the in-memory retry; review stored history before trying again. The duplicate-confirmed guard remains server-side.

## Safe consolidation

Only the old multi-request `recordStatutoryLeave` sequence is replaced. The public method name and result shape are retained. Standalone draft/non-required calculation evidence and annual-holiday calculation functions remain available. The standalone helper refuses confirmed supported statutory results and directs callers to the complete bundle.

Direct browser writes to statutory entitlements are revoked. Triggers reject older split writes to supported statutory transactions and confirmed supported calculations, including attempts to change/delete an already confirmed calculation. Annual-holiday, public/alternative-holiday, final-pay and ordinary hours paths are not reclassified. Dependency review found no existing database entitlement writer; calculation table references were a reference validator and liability-review reader. Existing privileged transaction writers remain privileged; no broader client grants or RLS exceptions are added.

Applied migration: `20261018024842_market_atomic_statutory_leave.sql`. It adds a private operation table, one guarded transaction API and narrow triggers. The operation table has RLS enabled and no client privileges/policies. Authenticated SECURITY DEFINER access is deliberate and authorization-checked. Security-advisor findings for these objects are recorded as intentional; unrelated historical advisories remain open.

## Validation and rollback

- Full offline suite: 351 tests, including 13 new tests using the actual existing statutory engine and command functions.
- Managed rollback fixtures cover complete save/replay, conflicting retry, duplicate confirmed records, stale OWD/period revisions, used-day accumulation, stored capacity, NaN, changed rules, direct-writer denial, non-required results without OWD, read-only/foreign/anonymous boundaries and caller-transaction abort. Fixture operations, employees, profiles and businesses roll back; no pay run or payslip is created.
- The existing hours-leave fixture still passes. Its old expectation of an allowed direct statutory insert is updated to require the complete bundle; its hours, correction, replay, rollback, tenant and statutory-unit checks are retained.
- `public/payroll-nz-statutory-leave.js` and its rules/formulas are unchanged. No provider call, employee access link or real entitlement is created by testing.

A frontend-only rollback to an older split writer is insufficient after the direct-write restrictions. Prefer a forward fix. Emergency rollback needs a reviewed compensating migration restoring the preceding grants/triggers along with the preceding frontend; preserve operations and audit history, and do not erase applied migrations. Reopening the old split path reintroduces its partial-save risk.

## Still open

This is a backend/runtime hardening increment. The exposed legacy calculation methods do not constitute a complete manager-facing statutory leave editor. Employee request approval remains a scheduling decision. A reviewed request-to-payroll bridge, confirmed-leave corrections, annual/final-pay workflows and guaranteed once-only consumption of statutory calculations across pay runs still need separate work. The current draft inclusion path reads unassigned confirmed calculations; this release does not add a consumption ledger or assert that approval automatically pays leave exactly once.

Authenticated visual/device/accessibility and true multi-session load acceptance remain uncompleted behind Market's existing Netlify team protection. Payslip/timesheet self-service, opening-balance conversion, restore rehearsal, provider and accountant/payroll acceptance and the wider commercial roadmap remain open.
