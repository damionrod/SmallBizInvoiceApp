# V61.86 — Subscription status synchronisation

## Problem and correction

Stripe recorded a completed Pro subscription checkout, but Frindly remained on
Trial because the subscription webhook tried to read billing dates from fields
removed in newer Stripe API versions. This raised `Invalid time value` before
the subscription update could be saved.

The webhook now reads billing dates from the recurring subscription item, with
support for the older subscription-level date fields. Frindly Checkout creates
one recurring plan item. Missing or invalid dates reject the event for retry
instead of inventing a billing period. Subscription database update errors also
return a failure so Stripe can retry rather than acknowledge an unsaved change.

Reference:
https://docs.stripe.com/changelog/basil/2025-03-31/deprecate-subscription-current-period-start-and-end

## Scope

Only one existing source file changed since v61.85:
`supabase/functions/stripe-webhook/index.ts`.

Its source import now resolves to the existing `../_shared/payment-config.ts` in
the repository. The deployed bundle uses the equivalent `./_shared/` path.
The shared configuration file itself is unchanged.

No frontend, subscription price, checkout creation, Stripe mode, database schema,
RLS policy, invoice settlement, fee, receipt, or referral logic was changed.
The earlier invoice-payment and automatic-checkout-redirect fixes are retained.
This release adds one regression test file and this note.

## Applied deployment and record correction

The corrected `stripe-webhook` was deployed as version 13 to the connected
Frindly Supabase project. The deployed source and shared dependency were read
back and matched against the tested package. Existing Stripe signature
verification and the function's `verify_jwt = false` setting were retained.

The existing CareClean subscription record was reconciled with the matching
active Stripe test subscription and its completed, paid Checkout Session.
Exactly one Frindly subscription row was updated to Pro / Active / monthly,
with the existing Stripe customer and subscription IDs and the billing period
23 September–23 October 2026. The stale trial end date was cleared. Its record
ID, creation date and invoice-limit override were preserved.

No Stripe subscription or payment was created, changed or cancelled. No signup
or payment needs to be repeated. Stripe remains in test mode.

## Validation

```bash
node --test tests/v6186-stripe-subscription-sync.test.js
```

Tested with Node.js 24.19.0. Eight behavioral tests execute the actual webhook
against isolated Stripe/database fixtures. They cover:

- Completed Pro checkout using the new billing-date format.
- Creation, renewal, cancellation, trial and past-due status handling.
- Compatibility with older event snapshots.
- Invalid dates and database failures.
- Repeated events updating the same record.
- Connected invoice payments using their existing settlement path.
- Missing and invalid signature rejection.

The tests reproduced the original error before the correction. Afterward, all
25 local test files passed; the separate authenticated HTTP/database test was
skipped because its test credentials were not available. The live subscription
record was read back and confirmed as Pro / Active with the expected dates.

These checks did not submit a fresh Checkout purchase or resend a signed Stripe
event. The business owner's signed-in screen should be refreshed to confirm the
display. No frontend file was changed.

## What to do now

Refresh https://frindly.co.nz/#settings/subscription while signed in to CareClean.
The plan should show Pro and the status Active. A Netlify redeployment is not
needed for this already-deployed backend fix. Keep this full source package in
GitHub so later function deployments retain the correction.

For a separate Supabase environment, after linking the intended project, deploy
only the changed function:

```bash
supabase functions deploy stripe-webhook --no-verify-jwt
```

No database migration is required. The one-time CareClean record correction was
performed separately and is not an automatic migration in this package.
