# Frindly v62.25 — reliable import review

18 October 2026. Isolated Market release; no Main deployment or production migration.

## Behaviour

Rebuilding a review replaces all sheets, mappings, logical records, source links and saved mapping profiles together. If any sheet fails validation, the previous review survives unchanged. A second browser with an outdated review must reload. Confirmation saves the user's decisions and imports the records in one transaction; retries return the completed result without importing again.

Completed source evidence cannot be rewritten or deleted through an older importer. All source rows must be linked to exactly one reviewed logical record before Smart Migration can confirm. This check also protects the older confirmation endpoint. Raw-row and logical-record IDs are assigned explicitly at staging, so capped API responses and repeated hashes cannot silently lose or merge links. Remapping paginates source reads, and counters use exact counts.

Duplicate classification is calculated against previously imported records by the database during review. Analysis alone does not mark a document as already imported. Existing native-document collision guards, domain permissions, uploader access, tenant checks, subscription rules and financial validation remain in place.

## Limits and next work

This release preserves evidence needed for a correct conversion; it does not implement the shared pre-migration paid-balance authority. Part-paid native imports and starting-balance posting remain blocked until payment guards, recalculation, credits/refunds, reports and conversion posting use that authority consistently.

Initial upload/staging still uses multiple requests. An interrupted upload may leave an incomplete batch; confirmation is blocked rather than silently accepting missing rows. Automatic cleanup of abandoned uploads remains future work. Duplicate policies across independently simultaneous batches require further concurrency acceptance; do not describe this release as universally race-free.

The rollback fixtures found a separate existing business-deletion audit foreign-key failure. The evidence trigger permits the existing whole-business cascade, but the pre-existing financial audit trigger can still reject it. No live business was used or deleted. This needs a dedicated audited-deletion correction.

Market keeps outbound services and Stripe disabled and Netlify team protection enabled. Hosted Stripe/promo acceptance, authenticated browser checks, leave/self-service, payrun approvals, backup/restore and accountant/payroll acceptance are not marked complete.

Rollback must coordinate frontend and Edge versions: the new Edge requires an expected review revision, which the previous frontend does not send. Restore the previous Market frontend and its matching Edge together if needed. Retain applied SQL history and completed evidence; any database reversal requires a reviewed compensating migration.
