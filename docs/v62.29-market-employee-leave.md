# v62.29 Market employee leave requests

Scope: isolated Frindly Market only. Main, live Frindly, existing memberships, payroll calculations, balances and financial records are unchanged. All fixture data rolls back; no real employee access was enabled or invitation sent by this release.

## Use

1. Open **Payroll → Leave requests**. An owner/admin with Payroll write access sees Employee leave access.
2. Choose an existing employee and enter the exact email of their confirmed existing account. Verify the identity and confirm Link account. The server creates only a leave-page association, not a business membership or permission to use Payroll. The same account can represent only one employee in each business. An existing link can be disabled or explicitly replaced using its loaded revision.
3. Share the employee leave-page address manually through your normal process. No automatic invitation/recovery/provider call is enabled. Market still requires Netlify team access before the application sign-in page.
4. The employee signs in on `employee-leave.html`, chooses their workplace, leave type, dates, requested amount and unit. No medical reason or supporting document is collected. A submitted request is pending; the employee can cancel it while pending.
5. A different Payroll manager approves or declines the saved request. Declines need a short explanation visible to the employee. Approval is a scheduling decision only. The employer must separately process leave using the existing payroll workflow; the UI states this on both pages. An approved request cannot be cancelled through this first slice; contact the employer to handle the correction.

No available leave types means the employer must configure Payroll first. The page does not guess an entitlement or display an unknown entitlement as zero. Two half-day requests on the same date are conservatively considered overlapping; employees should submit one combined request or ask the manager to review it. Dates cover a maximum 366-day difference; quantities must be positive, up to 10,000, with at most two decimals. Requests are not day/week entitlement calculations.

## Boundaries and failure handling

- Portal access does not depend on an email match at login. Only an explicitly stored user-ID link authorizes access. Employee email fields remain untouched. Deleted/banned/unconfirmed accounts, disabled links, archived/inactive/terminated employees, unavailable businesses or Payroll entitlement cannot use the employee API.
- Narrow APIs allowlist own-record fields. Raw link/request/operation tables have RLS enabled and no anon/authenticated/PUBLIC grants. Existing employee/payroll policies are unchanged. No bank, IRD, salary or other employee details are returned by the portal.
- Manager reads require Payroll read access; decisions require Payroll write access; linking also requires owner/admin team-management access. Current business is checked. A request preparer or currently linked employee cannot approve their own request even if they are a manager.
- All link and request mutations share a per-employee transaction lock. Creates check inclusive date-range overlap after the lock; cancellation/decisions compare the stored revision. A command commits request, audit and replay evidence atomically. The link writer rechecks authority after waiting. These locks are implemented and rollback-tested, not a measured simultaneous load test.
- Exact operation-ID retries return the saved result after current authorization is rechecked. Reusing an identifier for different actor/input fails. The UI blocks duplicate clicks and retains an uncertain action's original ID/input for retry in that page session. Closing the page discards that in-memory retry; refresh/history plus server overlap/revision guards prevent an accidental repeat from silently creating an overlapping request.
- Read lists paginate 100 at a time with exact totals. Manager employee access lists stop explicitly above 1,000 employees, rather than showing an incomplete list. Source strings are escaped; account/business changes invalidate pending UI responses. The separate employee session key preserves the accounting application's session.
- Request records and links protect employee history from direct employee deletion. Disable access and make the employee inactive/terminated rather than deleting them. Parent-business foreign keys retain cascading lifecycle behavior; the separately recorded pre-existing financial-audit business-deletion defect is not fixed here.

If emergency access suspension is needed, use a separately reviewed compensating migration to revoke EXECUTE on the four new authenticated APIs; retain request/audit history. Do not drop the tables or erase applied migrations. No change is deployed to Main in this release.

## Evidence and remaining gates

Full offline regression suite: **338/338**, including 15 actual UI/command tests in `tests/market-employee-leave.test.cjs`. Managed fixture `ops/market/tests/employee-leave-requests.sql` passes and rolls back all links, requests, operations and fixture business/profile/membership changes. It covers create/retry, conflicting retries, inclusive overlap, invalid numeric/date input, own/other employee isolation, raw-table denial, cancel/decline/approve, stale revisions, manager self-approval, revoked/terminated access, read-only/cross-business callers and canceled Payroll access. Existing leave balance, calculation and transaction counts do not change on approval.

Security advisors were reviewed. Guarded authenticated SECURITY DEFINER APIs and RLS tables without policies are deliberate: no client table privileges exist. This is not a claim that all historical advisories are resolved. Supabase's [RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) and the official supabase-js release were checked; the new page pins its SDK version to 2.118.0.

Authenticated browser/device/keyboard/zoom acceptance remains blocked by the existing Netlify team login in the shared browser. No protection was removed. Existing-account onboarding, invitation/recovery, own payslips/timesheets, approved-request correction, statutory save atomicity and any leave-to-payroll bridge require separate scoped work. The overall roadmap and commercial acceptance are not complete.
