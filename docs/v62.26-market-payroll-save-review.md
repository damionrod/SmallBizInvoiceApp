# Frindly v62.26 — payroll save and review

18 October 2026 NZDT. Scope: isolated Frindly Market only. Main/live is unchanged.

## What changes for users

- Employee details and recorded leave hours have separate saves. Recording hours saves history, balance and audit together. Correcting a balance requires a reason and refuses an out-of-date balance. Existing day/week statutory entitlements remain in their statutory workflow.
- A calculated or finalised pay run saves its employees, lines, payslips and financial entries together. A failed step rolls the whole save back. Retrying an uncertain save reuses its request identifier; a changed request cannot reuse it.
- Payroll settings have an optional **Pay-run approval** control, off by default. An owner/admin with Payroll write access can turn it on or off. When on, **Submit for approval** saves the figures. Another Payroll user with write access opens **Review pay run**, then **Approve and finalise**. The preparer cannot approve their own submission. A change to saved evidence requires resubmission.
- Approval uses the saved values and existing accounting posting. It does not send payments, emails or IRD filings. Disabling approval does not automatically finalise pending runs.

## Implementation and safe cleanup

Canonical UI: `public/payroll.js` and `public/index.html`. Removed the employee-detail save's unconditional balance upsert and the browser's split pay-run delete/insert/update sequence. They are replaced by bounded, authenticated, business-scoped database functions, not additional competing writers. Old root runtime copies and applied migrations are retained.

Market migrations:

- `20261017224555_market_atomic_leave_hours.sql`
- `20261017230343_market_atomic_payroll_review.sql`

The database owns request identity, timestamps, parent/child locks, stale-version rejection, approval evidence and auditing. Review settings use revision checks. Finalisation serializes per business before the existing duplicate-pay check. Child edits lock their parent and invalidate the save revision. Approval fingerprints cover saved run, employee, line, payslip and financial evidence. Public/anonymous execution is revoked. Owner/admin controls cannot be changed by ordinary Payroll users.

A pre-existing finalised-child trigger accessed payslip-only fields on employee rows. Its condition now checks the table before reading those fields. The existing immutability guard remains in place.

## Validation and limits

Full offline suite: **290/290 passed**. Tests execute the actual browser save/review functions, including original calculated totals and links, double-clicks, uncertain network retries, stale context, approval permissions, escaped employee names and unchanged statutory blockers.

Managed Market database fixtures (`ops/market/tests/leave-atomic.sql` and `payroll-atomic-review.sql`) run inside rollback subtransactions. They cover atomic history/balance saves, stale corrections, cross-business denial, non-finite amounts, invalid timesheets, failure during replacement, missing payslips, duplicate financial entry types, period readiness, approval-off finalisation, preparer rejection, changed-evidence rejection, idempotent approval and exactly-once journal posting. No fixture records remain.

Supabase security advisors were reviewed. The request-operation table deliberately has RLS with no client policies and no client grants. Authenticated SECURITY DEFINER notices are expected for these guarded transaction APIs; anonymous access is revoked and their business/role boundaries are tested. Existing project advisories remain a separate backlog; this is not a clean-security certification. See [Supabase database lint guidance](https://supabase.com/docs/guides/database/database-linter).

Concurrent multi-session load, authenticated desktop/mobile/keyboard/zoom checks and accountant/payroll acceptance remain uncompleted. Netlify team protection still blocks the shared browser from entering the Market app; protection has not been removed. Existing payroll calculations, tax rules and statutory day/week workflows are not redesigned here. Those statutory workflows still contain separate requests and need their own atomicity work. Employee self-service is not added.

## Deployment and rollback

Publish only `market/frindly-market` to the isolated Market site, using `node scripts/build-market.cjs`. Match the remote Git tree to the tested local tree and the published deploy to that branch's commit. Outbound services and Stripe remain disabled. Main's new payroll/leave API lookups remain absent.

For frontend rollback, use a verified Market deploy. The older leave editor's split writes are deliberately rejected by this database boundary, so reverting to v62.25 alone does **not** restore its leave editing. Prefer a forward UI correction. Any full rollback of the hours boundary needs a reviewed compensating migration and would reintroduce the old split-save risk; never erase migration history or disable audit. Do not remove approval guards while a business has approval enabled.
