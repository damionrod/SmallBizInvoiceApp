# v61.90C — why the two-photo invoice did not populate

## Findings, 24 September 2026

1. The frontend supplied `{ documents: [page1, page2], business_id }`. The live `scan-expense-document` Edge Function was still version 10 (updated 10:06 UTC), accepting only top-level `file_base64` and `mime_type`. It returned HTTP 400 when presented with the newer payload. Function request logs showed recent 400 responses; they do not identify which individual bill produced each response. Its old code proves the payload mismatch.
2. The main database lacked `purchase_document_items`, `purchase_invoice_reviews` and both v6190 RPCs. Even a successful header scan could not persist suggestions for the Expenses item-review screen. Old bill and payment rows were unaffected.
3. The frontend only auto-scanned when **exactly one** new file was selected. Selecting two images together required a separate **Scan all pages** tap. Errors from the Edge Function were replaced by a generic message, making the first failure hard to see.
4. A `null` amount from uncertain OCR was being converted by JavaScript `Number(null)` to zero. This could overwrite the amount on a draft bill and label an unknown GST value as no GST.
5. On an already saved bill, the review screen presented a blank row if no proposal had been saved; it did not try to scan its attached pages. It rejected all AI suggestions when OCR misread a bill total or supplier spelling, even though the user still needed to review the individual items.

## Corrective work

- The v6190 purchase-review migration was applied to the **main** Supabase project. The two tables and RPCs were verified present. No existing supplier bills, payments, bank allocations, GST returns or module entitlement records were edited; there were zero old optional-module item reviews to copy.
- The live `scan-expense-document` function was updated to **version 12**. It accepts ordered `documents` while retaining the original single-file input for older clients. It sends all images in one request, assigns source page numbers, and detects conflicting invoice identities. The deployed source was read back and verified. The revised source also avoids inferring a supplier-wide no-GST default from an unreadable GST amount.
- The frontend in this ZIP auto-scans two or more selected images, queues a new scan if pages change, retains manual inputs, shows the server error, and leaves unknown OCR figures unknown. Opening a saved bill without complete suggestions scans its attached pages; adding a page rescans the whole bill. If OCR reads the header imperfectly, its editable line suggestions remain visible with a warning. **Saving still requires all item ex-GST and GST amounts to equal the recorded bill exactly.**

## Evidence and limits

- Isolated database transactions previously checked two attachments, rejected duplicate pages and unbalanced saves, and confirmed optional module on/off behavior. Fixtures were rolled back. The Edge Function deployed and compiled on the isolated project before updating main.
- The main project was checked after the changes: scanner v12 active, both review tables and RPCs present, table RLS enabled, anonymous read denied. No production user transaction was created for testing.
- Local tests: `node --test tests/*.test.js` **20/20** passed; modified browser JavaScript passed `node --check`. There was no authenticated end-to-end AI scan using the customer's two original image files, and no phone/desktop browser run in this workspace. The exact OCR accuracy of those particular photos therefore remains unverified.

## What the user can do now

If the two pictures are **already attached to a saved bill**, open Expenses → find that bill → **Review items** → **Scan all pages**. With the existing frontend this manual tap is still necessary. The live backend now accepts both images, and the bill total must reconcile before confirming. After deploying the frontend from this ZIP and refreshing the browser, selecting two photos together and opening a saved bill with no suggestions trigger scanning automatically. Uploading to GitHub may trigger Netlify if the branch is connected; this release did not perform a Netlify deployment.

The review remains an operational classification and estimated-summary input. It does not automatically post cost of sales, asset balances, depreciation or an IRD tax deduction.
