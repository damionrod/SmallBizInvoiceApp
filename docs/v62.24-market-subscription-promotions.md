# Frindly v62.24 — subscription promotion controls

18 October 2026. Scope: the isolated Frindly Market branch and database only.

## Customer and super-admin behaviour

Super Admin → Subscription & Billing → Subscription promo codes provides a master switch, new-code form and per-code enable/disable buttons. Codes start disabled. The master switch also starts off. Terms are fixed after creation; a different deal requires a different code. All changes have an actor, timestamp and revision audit. Concurrent administrator saves fail with a reload instruction instead of overwriting each other.

Customers enter an optional code in signup or Choose your plan, before secure Stripe Checkout. The server checks the signed-in business owner's permission, plan price, master switch, code, interval and expiry. It applies a Stripe coupon so Stripe displays the discount and price before payment. The browser never sets a percentage, coupon ID or amount. No-code checkout does not depend on the new schema.

Supported offers: whole percentage 1–100%; monthly, annual or both; first payment or ongoing renewals; optional expiry. A first-payment annual offer discounts the first full annual invoice. An ongoing offer continues on that subscription. These codes are reusable and have no redemption cap or customer-specific allocation. Existing paid-subscription upgrades/downgrades do not accept a newly entered code. Existing discount-sensitive plan-change guards remain intact.

One offer applies at a time. An existing referral welcome reward is preserved; entering a promo code alongside it returns an explanation instead of silently stacking or replacing it. Subscription promo codes do not apply to customer invoice payments, community advertisements, or Stripe Connect.

Disabling a code or the master switch stops new discounted checkouts. Already issued payment pages remain valid for up to 31 minutes. Accepted subscription discounts are not removed. The endpoint rechecks controls before and after session creation and expires a new session if controls changed before returning its URL. Expiring offers stop accepting new checkout requests 31 minutes early because Stripe requires a minimum 30-minute session window. This is not an atomic transaction across Stripe and Postgres.

## Implementation and cleanup scope

- One dedicated shared server helper owns code normalization, eligibility and immutable coupon verification.
- Existing subscription Checkout remains the only billing entry point. Existing price verification, owner access, plan-change handling and signed webhook processing are retained.
- Three new tables hold global configuration, immutable offers and audit history. RLS and grants prevent ordinary users from listing or changing codes. The public capability RPC exposes only an enabled/disabled boolean.
- Canonical `public/` UI is changed. Legacy root UI copies remain retained as documented in the cleanup roadmap; they are not the Market runtime.
- No unrelated legacy files, financial tables, payments, accounting records or subscribers were deleted or rewritten.

Migration applied to Market: `20261017220141_market_subscription_promotion_controls.sql`. The administration RPC is `v6224_subscription_promotions`; public visibility uses `v6224_subscription_promotions_available`.
