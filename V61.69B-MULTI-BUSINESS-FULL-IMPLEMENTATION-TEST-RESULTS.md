## Gate C — provisioning

**PASS — migration/provisioning simulation.** A transaction/rollback simulation created a business, Owner membership, Trial subscription and Financial settings together; the transaction was rolled back and production counts remained unchanged.

**STATICALLY VERIFIED — atomicity.** `v6169b_add_business()` is one PostgreSQL function invocation. Any exception aborts the statement/transaction; `active_business_id` is updated only after required bootstrap inserts succeed.

**STATICALLY VERIFIED — clean tenant.** The provisioning migration does not insert/copy customers, suppliers, invoices, quotes, expenses, attachments, employees/history, bank transactions, GST returns, jobs, Accountant mappings, Xero mappings or tax history. It creates normal clean business defaults only.

**STATICALLY VERIFIED — bootstrap.** New tenant gets business row, active Owner membership, Trial subscription, Trial included modules, Financial settings/mappings, expense categories, Payroll settings and clean business settings. Existing Payroll first-use seeding supplies detailed Payroll defaults after the new business is active.

**PASS — RPC exposure.** `anon` cannot execute `v6169b_add_business`; `authenticated` can. The RPC itself requires an authenticated user, an authorised current business and Owner role (or controlled Super Admin).

**REQUIRES AUTHENTICATED E2E — failure rollback.** Browser-level forced-failure testing should verify no partial tenant is visible after an actual RPC error.

## Gate D — UX and switching

**STATICALLY VERIFIED.** Existing single-business flow remains login → app. Switch Business remains hidden with one active membership. No workspace selection screen/login step was added.

**STATICALLY VERIFIED.** `+ Add another business` is Owner-only in the UI, uses a short Business name + Country form, calls the controlled RPC, and reloads the page after success.

**STATICALLY VERIFIED.** Existing full-page reload switch mechanism remains. `my-businesses` now resolves current context using hardened `current_business_id()` rather than echoing stale profile fields.

**STATICALLY VERIFIED.** If current membership becomes invalid, startup may call `recover-current`; the server chooses another active membership, updates the profile, then the frontend resolves `current_business_id()` again before rendering. It does not continue rendering the stale business.

**REQUIRES AUTHENTICATED E2E.** Execute A → B → A → B → A with RED/BLUE settings and inspect every listed Settings/module surface. Source paths remain business-ID scoped and the existing `_settingsBusinessId` cache architecture is preserved, but zero-contamination is not claimed as browser PASS.
