## Root cause
The affected modules were not all using browser localStorage. The broader common defect was that several runtime loaders issued operational SELECTs without an explicit active `business_id` predicate and relied on RLS alone. In a multi-membership identity this is unsafe for rendering: membership-visible records can enter the module result even though another business is selected. Several loaders also retained their previous in-memory arrays/DOM when a request failed or while a new request was loading.

### Quotes
`job-costing.js` loaded `quotes`, `job_costings`, and customers without an explicit active-business predicate. Quote error handling returned without first clearing counters/table content. Fixed by active-business predicates, empty/error fail-closed rendering, business-scoped quote lookup, and business_id on newly created quotes.

### Expenses
`expenses.js` reference data was already business-filtered, but the main expense loader was not. It also only replaced `state.expenses` after a successful response, allowing prior state/DOM to remain during a new tenant load or error. Fixed by clearing operational state first, rendering empty first, querying by active business, failing closed on error, and discarding a response if the active business changed while it was in flight.

### Bank Reconciliation
Core bank account, bank transaction count/queue/history and rule queries were not consistently explicitly business-filtered. Module state was initialised once and was not modelled as belonging to a specific business. Fixed by explicit active-business filters and business-aware state reset before loading/reloading.

### Payroll
The primary Payroll loader set `state.businessId`, but most operational queries relied on RLS and did not explicitly filter by that business. The previous operational arrays were retained until Promise results returned. Fixed by clearing operational Payroll arrays first, filtering employees/timesheets/pay runs/children/documents/jobs/customers by the captured active business, and discarding results if business context changes during the request. Payroll settings/defaults remain legitimate business configuration and are still provisioned per business.

### Financials / GST
Most Financials queries were already explicitly business-scoped. Hardened the runtime lifecycle by emptying operational arrays before refresh, discarding an in-flight response if the active business changes, and removing fallback to the previous tenant's in-memory Financial settings when the new tenant has no settings row/result.

### Already appropriately scoped / audited
`job-profitability.js` and `accountant-centre.js` already use explicit `business_id` filters on their operational loaders. V61.69C already hardened invoices/customers/recurring invoice browser fallback behaviour. These files were not changed except their script URLs are cache-busted by `saas.js` so the deployed browser cannot retain an earlier runtime module version.

## Architectural rule applied
Authenticated operational/accounting state is cloud-authoritative, explicitly active-business scoped, and fail-closed. Empty cloud results are empty. A load starts from empty operational state. Errors do not preserve another tenant's records. Captured-business request guards discard stale responses after a tenant change. Legitimate business settings/defaults remain separate from operational records.
