## Root cause
V61.69D changed the loader from `state.employees = emp.data || []` to `state.employees = emp.error ? [] : (emp.data || [])` (and equivalent handling for other Payroll arrays). That was secure against stale-tenant display, but it collapsed a failed Care query into the exact same UI state as a successful empty Bingo query. It also trusted the UI business object as the query context without independently resolving `current_business_id()` inside Payroll immediately before loading.

Therefore a transient/context/RLS/query failure during the Care reload was rendered as a legitimate zero-employee business. The browser's underlying Supabase error was not surfaced by V61.69D, so its exact server error text cannot be recovered after the fact. The exact query whose failure was hidden for the employee screen was:
`payroll_employees.select('*').eq('business_id', requestBid).order('last_name')`.
Live authenticated SQL simulation confirms that query shape returns Care's 4 rows when Care is the authorised current business.

## V61.69E correction
- Payroll now resolves backend `current_business_id()` before operational loading and requires it to equal the UI business ID.
- Operational arrays are cleared before loading, preserving V61.69D fail-closed isolation.
- `v55_seed_payroll_defaults` and `payroll_settings` failures now produce a safe visible Payroll load error.
- All operational Promise results are checked as a group. Any failure leaves all Payroll operational arrays empty, does **not** set `state.loaded=true`, and displays `Unable to load Payroll data...` rather than the legitimate empty-business message.
- A successful query returning `[]` remains a valid empty tenant.
- Late responses are still discarded when the UI business changes.
- Payslip history/chooser reads now also explicitly include the current `business_id` as defense in depth.
- No V61.69D tenant-isolation behavior was reverted.
